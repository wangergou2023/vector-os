# wire-os 开发总结 (2025-05-30/31)

## 一、架构演进

```
之前: vic-cloud + daima-agent / robot-mcp  (3 二进制, 竞争 :443)
现在: vector-mcp                       (1 二进制, 双模式)

vector-mcp 双模式:
├── 无参数 → Gateway (gRPC :443 + 引擎 IPC)
└── --client-only → MCP 客户端 (连 localhost:443)

部署:
  vic-cloud.service → /anki/bin/vic-cloud                  [Gateway]
  daima.service     → popen /data/daima/bin/robot-mcp --client-only  [Client]
```

## 二、播放管线 6 补丁

| # | 补丁 | 根因 | 文件 |
|---|------|------|------|
| 1 | 串行 TTS | BigModel 并发调用导致偶数句音频损坏 (HTTP 库线程不安全) | `tts_player.c` |
| 2 | `go Recv()` 消费响应 | gateway 的 engineProtoManager channel (容量1) 被堵死 → 引擎卡住 → 音频停止 | `audio_socket.go` |
| 3 | `<-recvDone` 等 Recv 退出 + 500ms 流间延迟 | 上一个 gRPC 流未完全清理 (recv drain 85-454ms) 就开新流 | `audio_socket.go` |
| 4 | 20ms chunk 节流 | 一口气发完 18s 音频 → robot 缓冲溢出 → 只播前 2 秒 | `audio_socket.go` |
| 5 | 静音 + sleep 音频时长 | 麦克风解开时 robot 还在播 → 拾取自己声音 → 假 VAD 触发新对话 | `tts_player.c` |
| 6 | 均衡合并分句 | tail merge 导致 71 字单句 (18s 音频) | `tts_player.c` |

## 三、功能添加

| 功能 | 说明 |
|------|------|
| 声源定位 | 4麦波束成形方向 (0-12) 注入 Agent prompt |
| 传感器 | 前向激光距离 + 4悬崖检测状态注入 Agent prompt |
| PCM 文本标签 | socket 协议传句子文本, 日志可看到每句对应 PCM |
| 全局 seq | 播放序号跨对话递增, 不重置 |

## 四、agent 上下文注入

LLM 每轮对话 system prompt 自动包含:

```markdown
### 通道附加要求
- 回答要尽量简短，控制在 1-2 句。
- 当前对用户说话声音来源方向: 0 (正前方, 角度约 0°)
- 前方障碍物检测: 无 (距离 200mm), 无遮挡
- 桌面边缘检测: 未检测到
```

## 五、TTS 分句策略

```
SOFT_LIMIT = 24 字
MAX_SENTENCES = 3

≤24 字 → 整句一次
>24 字 → 。！？切分 → ≤10字短句合并 → 均衡分配 → 最多3句
串行 TTS (BigModel 并发不稳定)
增益 1x (2x 削波导致滋滋声)
低通 4kHz + 24000→16000 降采样
```

## 六、关键路径

| `daima-agent/main/channels/vector/vector_channel.c` | VAD + PCM 缓冲 |

## 七、已知遗留

| 问题 | 状态 |
|------|------|
| 重启后 daima.service runtime link 丢失 | 需 SSH 手动 `systemctl --runtime link` |
| 重启后旧 gateway IPC socket 残留 | `robot-mcp: bind: address already in use` |
| `conn==nil` 但连接已死的检测 | 重连 goroutine 只检查 nil, 不检查连接活性 |

## 八、构建部署

cd ~/code/github/wire-os/daima-agent
./build-arm.sh

# 一键部署
cd ~/code/github/wire-os
./restore.sh <robot-ip>
